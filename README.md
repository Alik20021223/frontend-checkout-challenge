# Оформление заказа — решение тестового

Фронтенд магазина: каталог, корзина, оформление заказа с расчётом доставки и тестовая оплата картой с ожиданием результата. Бэкенд из задания не менялся, фронтенд лежит в `apps/web` (workspace `@checkout/web`).

Стек: Next.js 16 (App Router), React 19, TypeScript. Библиотеки состояния, форм и UI не использовались: весь общий код — свои небольшие модули, их проще показать и защитить.

Условия задания: [ASSIGNMENT.md](docs/ASSIGNMENT.md) · [INTEGRATION.md](docs/INTEGRATION.md) · [EVALUATION.md](docs/EVALUATION.md).

## Запуск

Нужны Node.js 24 и npm 11.

```sh
npm ci
npm run dev          # API на http://localhost:4000 и фронтенд на http://localhost:3000
```

Другие команды:

```sh
npm run dev:api      # только бэкенд
npm run dev:web      # только фронтенд (API должен быть запущен)
npm run build        # контракты, API и production-сборка фронтенда
npm start            # собранный API
npm run start:web    # собранный фронтенд
npm run check        # prettier, тесты API, проверка OpenAPI
npm run typecheck -w @checkout/web
npm run e2e          # сценарный прогон Playwright по запущенному приложению
```

Адрес API можно переопределить переменной `NEXT_PUBLIC_API_URL` (по умолчанию `http://localhost:4000`). Для `npm run e2e` нужен браузер: `npx playwright install chromium` либо `PLAYWRIGHT_CHANNEL=msedge` / `chrome` для системного.

### Слой API

`createHttp` в `api/http.ts` — единственное место, где вызывается `fetch`. Он знает базовый адрес, ставит `Content-Type`, `Authorization` и `Idempotency-Key`, сериализует тело, отличает `204` от ответа с телом, разбирает JSON и снимает обёртку `data`. Любой неуспех превращается в `ApiError` с полями `status`, `code`, `message`, `fields`: сетевая ошибка получает код `NETWORK_ERROR`, ответ не в JSON — `INVALID_RESPONSE`, ошибка API — код и сообщение из тела. На `401` транспорт один раз создаёт новую гостевую сессию и повторяет запрос.

`api/index.ts` описывает методы в одну строку каждый: `api.cart.setItem(productId, quantity)`, `api.orders.create(body, key)` и так далее. Компоненты и хуки не видят `Response`, статусов и тел ошибок.

### Загрузка, действия и опрос

- `useResource(load, deps, options)` загружает данные при изменении зависимостей. Каждый запуск получает свой `AbortSignal`; предыдущий запрос отменяется, поэтому запоздавший ответ не подменит свежие данные. Опция `pollWhile` превращает загрузку в опрос: пока функция возвращает `true`, запрос повторяется через `pollIntervalMs`. Размонтирование компонента прерывает и запрос, и опрос. На нём работают каталог, способы доставки, расчёт, заказ, список попыток оплаты и отслеживание попытки.
- `useAsync(task)` — для действий пользователя. `run` никогда не бросает исключение: ошибка попадает в состояние, поэтому в компонентах нет `try/catch`. На нём работают корзина, создание заказа, попытки оплаты и имитация.
- `QueryState` рисует загрузку, ошибку с кнопкой «Повторить» или отдаёт данные в render-функцию, чтобы страницы не повторяли одни и те же три ветки.

### Идемпотентность и повторы

`idempotencyKey(scope, body)` хранит в localStorage ключ вместе с отпечатком тела. Пока тело не изменилось, повтор запроса после обрыва связи уходит с прежним ключом и получает уже созданный ресурс. Изменённое тело автоматически получает новый ключ. После успешного ответа ключ освобождается, и следующая попытка оплаты начинается с нового.

### Формы

`validation.ts` содержит правила полей, повторяющие ограничения из `@checkout/contracts`, одну функцию `validate` для всех полей и `serverFieldErrors`, которая переводит `fields[].path` вида `body/customer/email` в имя поля формы. `Field`, `SelectField` и `Choice` связывают подпись, поле и текст ошибки через `htmlFor`, `aria-describedby` и `aria-invalid`.

## Пользовательские сценарии

- **Каталог.** Товары из `GET /api/products`. Товар с нулевым остатком добавить нельзя. Для товаров в корзине кнопка заменяется на счётчик; количество ищется в `Map` по `productId`.
- **Корзина.** Количество меняется кнопками или вводом с клавиатуры; `0` удаляет позицию. После каждого изменения корзина перечитывается с сервера, состав и суммы отображаются из ответа API. Превышение остатка показывает сообщение сервера рядом с позицией.
- **Оформление.** Черновик формы хранится в localStorage и переживает перезагрузку и ошибки запросов. Расчёт (`POST /api/quotes`) запрашивается заново при смене версии корзины, способа доставки, пункта выдачи или адреса (адрес — после паузы 400 мс и только когда он проходит проверку). Кнопка отправки недоступна, пока расчёт не соответствует текущим полям. `409 CART_VERSION_CONFLICT` перечитывает корзину, `409 QUOTE_EXPIRED` — расчёт; форма остаётся заполненной, пользователю показывается подсказка подтвердить заказ ещё раз. Ошибки валидации сервера привязываются к полям.
- **Оплата картой.** На странице заказа берётся список попыток; активная продолжается, завершённая показывает результат и предлагает новую попытку. Форма оплаты — выбор тестовой карты из `GET /api/sandbox`, без ввода номера. После `POST /simulations` попытка опрашивается раз в секунду до `succeeded`, `failed` или `cancelled`; затем заказ перечитывается, и страница успеха показывается только при `status = paid` с сервера. Отказ и отмена различаются текстом, повтор создаёт новую попытку с новым ключом.
- **Наличные.** Заказ сразу получает `confirmed`, показывается сообщение «Заказ оформлен, оплата при получении» без формы оплаты.
- **Перезагрузка.** Токен сессии, черновик формы и идентификатор последнего заказа лежат в localStorage; ссылка «Мой заказ» в шапке ведёт к незавершённому или последнему заказу. Незавершённая попытка оплаты находится через `GET /api/orders/{id}/payments` и отслеживается до результата.

## Разбор участка обработки данных

`cartIndex` в `SessionProvider` — `Map<productId, CartItem>`, которая строится в `useMemo` одним проходом по `cart.items` и только когда с сервера пришла новая корзина, то есть после каждого изменения количества и при загрузке. Память: один `Map` на N позиций, промежуточных массивов нет.

Потребитель — каталог: при каждом рендере для каждого из M товаров нужно узнать, сколько его уже в корзине. С индексом это M обращений `Map.get` за O(1). Вариант `cart.items.find(...)` внутри `map` по товарам давал бы O(M·N) сравнений и создавал замыкание на каждый товар при каждом рендере, включая рендеры, где корзина не менялась. При четырёх товарах разница незаметна, но при сотнях карточек и частых изменениях корзины индекс окупается, а код остаётся таким же коротким.

Из той же серии: `indexOptions` собирает индекс пунктов выдачи и названий оплаты одним проходом по ответу `/api/checkout/options`, а `validate` обходит правила один раз и заполняет один объект ошибок, без промежуточных массивов и `filter`.

## Проверенные сценарии

Скрипт `apps/web/e2e/checkout.mjs` проходит по запущенному приложению в браузере и проверяет:

1. каталог из четырёх товаров, недоступный товар нельзя добавить;
2. добавление из каталога и изменение количества счётчиком, число в шапке;
3. ввод количества с клавиатуры, удаление позиции, итог корзины;
4. превышение остатка — сообщение сервера у позиции;
5. расчёт самовывоза и ошибки полей при отправке пустой формы;
6. курьер и адрес пересчитывают доставку с сервера (390 ₽, бесплатно от 5 000 ₽);
7. перезагрузка сохраняет заполненную форму и выбранную доставку;
8. заказ картой: отказ банка, повторная попытка, страница успеха с номером, составом и доставкой;
9. отмена оплаты, перезагрузка во время ожидания банка, успешный повтор;
10. заказ наличными: двойное нажатие создаёт один заказ (проверка через API);
11. ссылка «Мой заказ» после перезагрузки открывает последний заказ;
12. ширина 390 px: каталог, корзина и оформление без горизонтальной прокрутки.

Вручную проверены: остановка опроса при уходе со страницы (запросы прекращаются в Network), восстановление сессии после `npm run data:reset` (создаётся новая гостевая сессия, корзина пустая), работа формы с клавиатуры.

## Что не сделано

- Нет модульных тестов для хуков и транспорта; проверка держится на сценарном прогоне и ручных проверках.
- Интервал опроса задан константой в 1 с; заголовок `Retry-After` не читается.
- Корзина не знает остатка товара, поэтому в ней «+» ограничен только ответом сервера (в каталоге кнопка блокируется по `stock`).
- Изменение количества — это `PUT` и затем `GET` корзины, оптимистичного обновления нет.
- После сброса данных на сервере новая сессия создаётся молча; пользователь видит только пустую корзину.
